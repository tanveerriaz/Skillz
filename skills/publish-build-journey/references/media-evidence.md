# Media evidence workflow

## Select

Choose media that proves or explains one of these:

- The initial question or first attempt
- The mismatch or failure
- The correction
- The working artifact
- The environment or public event that changed the thinking

Prefer 3–6 strong visuals over a gallery.

## Verify provenance

Classify each asset:

- `live-capture`: captured from a verified public deployment
- `product-source`: already part of a public project repository
- `user-supplied`: explicitly provided by the user for this story
- `public-event`: from an approved public post or event source
- `generated`: created with an image/video model
- `sample`: illustrative data or fictional interface

Record the public source URL and capture date where applicable.

## Inspect the visible frame

Check for:

- Browser tabs, bookmarks, notifications, avatars, and account switchers
- Terminal paths, usernames, hostnames, commands, tokens, and unredacted logs
- Private repository names, internal domains, task names, and branch names
- Email, phone, IDs, account numbers, balances, or customer data
- Faces and names of unrelated people
- Street signs, room numbers, tickets, badges, GPS cues, and real-time location

Crop only when the remaining frame still represents the artifact honestly. Do not cover sensitive data with translucent blur; remove or use a fully opaque redaction.

## Sanitize

Create a derivative file. Apply orientation, remove metadata, and use a descriptive public filename. Never overwrite the source.

After sanitizing, inspect the derivative visually. Metadata removal does not remove visible secrets.

## Disclose

Use concise labels:

- “Live capture · public deployment · August 2026”
- “Generated concept · not the shipped interface”
- “Fictional banking demonstration · mock data”
- “Public event photograph · shared retrospectively with approval”

Alt text should describe what matters to the story, not infer identity, emotion, ethnicity, health, or other sensitive traits.
