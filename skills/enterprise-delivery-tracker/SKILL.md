# Purpose

Bring banking-grade delivery discipline to programme management without leaking any organization's specifics. Large, regulated programmes need consistent intake, prioritization, status, and governance — done in plain language, with no invented facts. This skill provides that structure generically, so it applies to any enterprise context.

# When to Use

Use when coordinating multiple teams against a programme, running an initiative intake-to-delivery pipeline, preparing a project status report (PSR) or executive update, or maintaining a RAID log for governance. Use it wherever enterprise regulatory or large-scale delivery needs structured tracking and reporting.

# Inputs

- The initiatives/workstreams and their current state.
- Risks, assumptions, issues, and dependencies (RAID).
- The governance cadence and audience (delivery leads vs. executives).

# Outputs

- A structured initiative register (intake → prioritized → in delivery → done).
- A maintained RAID log.
- A project status report with executive summary, status by workstream, critical issues, and RAID highlights.
- Plain-language updates with no invented facts.

# Procedure

1. **Intake.** Capture each initiative with a clear problem statement, sponsor, and intended outcome. Don't let undefined work enter delivery.
2. **Prioritize** against agreed criteria (value, risk, regulatory deadline, dependency order); make the basis explicit.
3. **Track delivery status** per workstream with an honest RAG (red/amber/green) and a one-line "latest update".
4. **Maintain RAID.** Log risks (with likelihood/impact and mitigation), assumptions, issues (with owner/action), and dependencies (with the team relied upon). Keep it current.
5. **Report for the audience.** Executive summary leads with what matters; detail sections cover status, critical issues, and RAID. Keep language plain — no jargon, no hype, no invented facts.
6. **Govern.** Flag items needing decisions or escalation explicitly so governance forums can act.
7. **Keep it factual.** Updates reflect actual state; if status is red, say so and why.

# Quality Checklist

- [ ] Every initiative has a problem statement, sponsor, and outcome
- [ ] Prioritization basis is explicit
- [ ] Status uses honest RAG with a current latest update
- [ ] RAID log maintained with owners and actions
- [ ] Reports tailored to audience, in plain language
- [ ] Decisions/escalations flagged for governance
- [ ] No invented facts; red is reported as red

# Edge Cases

- **Conflicting priorities across sponsors:** surface the conflict and the trade-off for a governance decision rather than silently choosing.
- **Status pressure to show green:** report true status; mark amber/red with cause and mitigation.
- **Dependency owned by another team:** log it as a dependency with the owning team and needed date.
- **Regulatory deadline at risk:** escalate early; never bury a missed-deadline risk.

# Safety Rules

- Never include employer, client, or programme-identifying confidential details — keep it organization-agnostic.
- Never invent facts, dates, or status to fill a report.
- Never soften a real risk or issue to look good; governance depends on honesty.
- Keep all examples and data public-safe and generalized.

# Examples

**Good:** "Use this for enterprise regulatory initiative tracking where multiple teams manage intake, prioritization, delivery status, risks, issues, dependencies, and governance reporting." A PSR leads with an executive summary, shows three workstreams (1 amber: vendor dependency slipping), and a RAID log with owners and mitigations.

**Bad:** A tracker naming a specific bank's confidential programme, or a status report marking everything green to avoid a hard governance conversation.
