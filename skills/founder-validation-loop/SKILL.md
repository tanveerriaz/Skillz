# Purpose

Help solo builders and founders learn fast and compound their work. Builders generate many experiments; most insight and reusable value gets lost. This skill makes each experiment a deliberate test with a decision and a captured asset, so building becomes a compounding system rather than a pile of abandoned prototypes.

# When to Use

Use when starting a new experiment or side build, when deciding whether to continue/kill an idea, or when a prototype "worked" and you want to extract the reusable part before moving on.

# Inputs

- The idea or experiment and what you're trying to learn.
- The signal that would count as success or failure.
- Time/resource budget for the test.

# Outputs

- A one-line hypothesis and the cheapest test of it.
- The observed signal and a clear keep / kill / pivot decision.
- A captured reusable asset (skill, template, snippet, or note) regardless of outcome.

# Procedure

1. **State the hypothesis.** "I believe [X]. If true, I'd see [signal]." Make it falsifiable.
2. **Pick the cheapest valid test.** What's the least work that produces a real signal? Prefer a landing page, manual concierge version, or a tiny prototype over a full build.
3. **Set the bar in advance.** Decide what result means keep vs. kill vs. pivot before running — so you don't rationalize afterward.
4. **Run the test** and observe the actual signal (usage, replies, conversions, whether it works).
5. **Decide honestly:** keep (double down), kill (stop, no sunk-cost), or pivot (adjust the hypothesis).
6. **Capture the asset.** Extract whatever is reusable — a code pattern, a template, a checklist, a skill — and store it so the next build starts ahead. Even a kill yields a lesson worth capturing.
7. **Feed it forward.** Reusable wins become skills/templates in your library; insights inform the next hypothesis.

# Quality Checklist

- [ ] Hypothesis is one line and falsifiable
- [ ] Test is the cheapest valid way to get signal
- [ ] Success/failure bar set before running
- [ ] Decision made honestly (keep/kill/pivot)
- [ ] No sunk-cost reasoning
- [ ] A reusable asset or lesson captured
- [ ] Result feeds the next experiment

# Edge Cases

- **Weak/ambiguous signal:** treat as inconclusive; design a sharper test rather than forcing a decision.
- **Emotionally attached to the idea:** lean harder on the pre-set bar to stay honest.
- **"Successful" test, messy build:** still extract the reusable part before moving on.
- **No time for a full test:** shrink the test, not the rigor.

# Safety Rules

- Don't move the success bar after seeing results.
- Don't keep an idea alive on sunk cost alone.
- Keep captured assets public-safe — generalize anything tied to private data or clients.

# Examples

**Good:** "Hypothesis: builders want a skills marketplace. Test: a one-page repo + post; bar: 25 stars in a week. Result: 60 stars → keep. Captured: the repo structure as a reusable template."

**Bad:** Spending a month building a full product, getting no usage, and starting the next thing from scratch with nothing reused and no recorded lesson.
