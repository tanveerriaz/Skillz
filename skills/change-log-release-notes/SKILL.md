# Purpose

Create a reliable audit trail of changes and turn it into trustworthy release notes. Two problems this solves: changes get forgotten between sessions, and release notes get fabricated from memory. The fix is a single dated log appended to as work happens, and release notes derived strictly from those logs — never invented.

# When to Use

Use throughout development to append a log entry after each change, and at release time to generate notes. Trigger phrases: "log this", "update the change log", "prepare release notes", "what's going into this release", "summarize changes".

# Inputs

- The change just made: the request, what was searched/found, the plan, files changed, and test results.
- For release notes: the set of daily log files for the period or version being released.

# Outputs

- A dated change log file, appended to across the day (e.g. `logs/03-Jun-26.md`).
- A release notes file derived from the logs (e.g. `release-notes/v0.9.3.md`), grouped into Features / Improvements / Bug Fixes / Security / Known Issues.

# Procedure

**Logging (during development):**
1. Append to today's dated log file; use one file per day, append-only.
2. For each change record: timestamp, the user instruction, discovery (searches run and what was found), the plan, files changed with one-line summaries, test results, and any risks/TODOs.
3. Keep entries factual and concise.

**Release notes (at release time):**
1. Read only the relevant daily log files — do not pull from memory or invent items.
2. Group changes logically into: New Features, Improvements, Bug Fixes, Security / Auth, Known Issues / Follow-ups.
3. Rewrite each item in simple, user-readable language (no internal jargon, no file paths).
4. Write to a versioned or dated release-notes file.

# Quality Checklist

- [ ] Every change has a log entry with files touched and test result
- [ ] Log is append-only and uses one file per day
- [ ] Release notes derive solely from the logs
- [ ] No invented features or fixes in the notes
- [ ] Notes grouped by category and written in plain language
- [ ] Security/auth changes called out explicitly

# Edge Cases

- **No log entries for a period:** state that there are no recorded changes rather than guessing.
- **A change spans multiple days:** reference all relevant daily logs when composing notes.
- **Internal-only refactor:** include in the log, but in release notes summarize as an improvement without exposing internals.
- **Sensitive details in a log entry:** keep logs free of secrets; reference what changed, not credential values.

# Safety Rules

- Never fabricate release-note items not backed by a log entry.
- Never put secrets, tokens, or private URLs in logs or notes.
- Never overwrite prior log entries — append only.

See `templates/daily-log.md` and `templates/release-notes.md`.
